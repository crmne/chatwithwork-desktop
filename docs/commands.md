# Running commands

Status: **built on Linux, tested on macOS and Windows.** On macOS, commands were tried for real on 2026-10-27 on a Mac mini (Apple silicon, macOS 27) paired with staging: approved runs, a failing one, the network off and on, the CPU limit, a background run with its output followed in `cww tui` and stopped from there and from a chat, and the sandbox refusing to read or write outside its folder. Up to 0.6.2 every command on a Mac failed to start ("resources.memoryMb is not supported by the 'seatbelt' backend"); the tests ran with the fix that followed. On Windows, commands run from Windows 11 24H2 with the August 2026 update ([Windows](#windows)); the tests that run them for real passed on 2026-10-27 on a Windows 11 26H2 virtual machine, in a standard user's desktop session, and on Windows 11 on Arm (25H2) in CI. The same day, on that virtual machine, the installer CI built, paired with staging as a standard user, ran `dir`, `git status` and `npm test`, a failing build, a background run followed in `cww tui` and stopped from a chat, a command approved in `cww tui`, and a read outside its folder that the sandbox refused. In a shared folder that allows changes, you can also allow commands. Chat with Work can then run one line of shell there (Windows PowerShell on Windows), like `bin/rails test` or `npm run build`: each approved in Chat with Work, or run without asking in a chat where you chose "Allow everything" as the permission mode ([Who approves](#who-approves)). The wire details are in [PROTOCOL.md, section 8.15](../PROTOCOL.md#815-commands), and the switch in [CONTROL.md, `roots_commands`](../CONTROL.md#roots_commands).

## Its network

A folder that allows commands has one of three levels, set on this computer only (the app's settings pane, `cww roots`, or `config.toml`):

- **None.** Nothing at all.
- **Local services** (the default, `local_services = true`). This computer's own services, without the internet: its loopback (a command's own `localhost:5432` reaches the PostgreSQL this computer serves on `127.0.0.1:5432`), its own addresses, and the networks of the containers and virtual machines it runs: Docker's `docker0` and Compose's `br-<network id>` (never another `br-` bridge, which can be the local network's), Podman's, libvirt's `virbr*`, CNI's, LXC's, LXD's and Incus's (172.17.0.4:5432, a container's own address, is this computer). Never the local network, never the internet, and name lookups fail, since a name server is outside this computer.
- **Local services and the internet** (`network = true`, "Internet"). Everything, as before 0.16.0: the internet and the local network, and this computer's services with them.

Narrowing a folder's network (to None, from the internet, or taking an exact address away) stops the commands running there, whose sandboxes were made with the wider one.

Folders that allowed commands before 0.16.0 keep their setting: with the network they keep everything, and without it they get local services, which they didn't have.

Exact addresses on the local network (a database on another machine, `192.168.1.20:5432`) can be allowed one by one (`reach` in `config.toml`, `cww roots reach <folder> <ip:port>`, or "Always allow" in the app's dialog), never a whole network. Each holds whatever the folder's level, "None" included, since it was allowed by name. Only private, link-local and shared (100.64.0.0/10) IPv4 addresses go there, never one of this computer's own or its containers' (those are local services), and anything else is the internet.

On Linux, a command's own servers keep working at every level: it listens on its own loopback, which is its own, and connects to itself there, and nothing reaches them from outside its sandbox. On macOS a command can't serve itself ([Per system](#per-system)).

### What it reaches, and what it never does

Local services are the TCP ports this computer serves on its loopback (or on every address) when the command starts, its own addresses and its containers' networks. A service started after the command is reached on the containers' networks and this computer's addresses, but not as the command's own `localhost`, which lists ports when the command starts: run the command again. A command connecting to a port this computer serves on its loopback reaches that service instead of anything of its own on the same port.

Some ports never are reached, at any level, on this computer's own addresses and its containers' networks, since each would let a command out of its sandbox rather than into a service:

- **2375 and 2376**, the Docker API over TCP (and Podman's, when served there): whoever reaches it can start a container that mounts any folder of this computer.
- **5900 to 5999**, VNC: this desktop's screen and keyboard.
- **6000 to 6063**, X11 servers listening on TCP, which take keystrokes and read every window.
- **9222**, Chrome's and Chromium's DevTools port, which drives that browser with every sign-in in it.
- **9229**, Node.js's inspector, which runs code in the process it inspects.
- **Desktop's own listeners** (the app's one-shot sign-in callback, anything else of its own), found by the programs that hold them.
- **The person's own programs' listeners on a port the system picked** (32768 to 60999 on Linux, 49152 to 65535 on macOS): a service meant to be found has a port of its own, while a random one is an editor's helper, a browser's debugger, or a sign-in's callback, meant for one program. A container's published port is Docker's, so it stays whatever its number; a rootless Docker's or Podman's on a random port doesn't.

Desktop's control socket is a Unix socket (a named pipe on Windows), which no command can see.

### What the result says

When the sandbox refused a command something, its result says what (`blocked`, [PROTOCOL.md 8.15](../PROTOCOL.md#815-commands)), so Chat with Work can say why it failed and offer what would let it through:

- **Connections**, on Linux with Bubblewrap: the sandbox's firewall copies each connection it refuses to Desktop (`NFLOG`, read inside the command's own network namespace), which places it from this computer's own networks: this computer, the local network or the internet, and names the service by its port. A name lookup is said by the name it asked for. A refused connection fails at once ("Connection refused"), rather than waiting minutes for a timeout. On macOS a refused connection fails at once too ("Operation not permitted"), but which one isn't said: Seatbelt's denials are in the system log, which Desktop doesn't read. Windows and Landlock don't say either.
- **Paths** outside the folder and the command's home, on every system, as a best guess from what the command printed: an error that sandboxes give ("Read-only file system", "Operation not permitted", "Permission denied") next to the path. A program that prints nothing, or prints the path differently, isn't caught, and a path a program couldn't use for another reason can be.

### Asking

When a command needs more than its folder allows, the person decides on this computer, never the server: Chat with Work's card about a blocked command opens the app on it, and a page there can ask the app (`computer.allowReach`, [desktop-app.md](desktop-app.md)), which asks in its own dialog, naming the bot, the folder and the service, as this computer places it: "Let Issue fixer reach PostgreSQL (172.17.0.4:5432) from App on this computer?" Allow once gives that one destination (the internet, for an internet address) to the next command in that folder, for that bot when one asked, and lasts until that command ends or 30 minutes pass. Always allow turns local services on for an address on this computer, adds the exact address to `reach` for one on the local network, and turns the internet on for one on the internet. Where this computer's sandbox can't give exactly that, the question says what it can: on macOS and Windows an address on the local network only with the internet, and on Windows nothing of this computer's own, which isn't asked at all. An "Allow once" never reopens a port no command reaches, and ends when this computer is paired again; one whose command didn't start (the computer was busy) waits for the next. Each answer is in the audit log (`root_reach_allowed`, `root_reach_declined`).

### Per system

- **Linux, Bubblewrap**: as above. Each command gets a network of its own through slirp4netns, whose firewall (in that network alone) accepts this computer's addresses and containers' networks and the loopback ports it serves (reached through slirp's gateway, and as the command's own `127.0.0.1:<port>` by an address translation in its namespace), refuses the rest at once, and logs what it refused. Where a run can't have a network of its own (slirp4netns, util-linux's `unshare` or iptables missing, or unprivileged network namespaces refused, as Ubuntu 23.10 and later do with AppArmor, though Bubblewrap itself still runs), a folder's local services give nothing and its commands run with no network, unlogged; a folder with the internet fails at once and says why, as before.
- **Linux, Landlock**: no network at all, local services included. Landlock (from its ABI 4) restricts which TCP ports a command connects to and binds, never which address, so it can't keep a connection to this computer's port 5432 from reaching another machine's: there a folder's local services give nothing, and a folder with the internet fails at once, as before. `roots` still says the folder's level; which sandbox a command gets is found when it starts.
- **macOS, Seatbelt**: the loopback ports this computer serves when the command starts, as `localhost:<port>`, which Seatbelt reads as every address of this machine on that port. Docker Desktop publishes containers' ports there. Containers' own networks aren't reachable from macOS anyway, and exact local-network addresses can't be given: Seatbelt names no address but `localhost`, so a folder's `reach` and an "Allow once" for the local network do nothing there, and only the internet reaches another machine. A command can't serve itself either, as before 0.16.0: Seatbelt can only let a command listen on "this machine", which takes connections from the local network too to a server listening on every address, so it isn't allowed.
- **Windows**: none or the internet. A process container never reaches this computer's own services (its loopback), and only an administrator's loopback exemption could change that, which changes the system for every app; so on Windows a folder's local services give nothing, `network_access` says `none`, and the app doesn't offer them.

## Where a command runs

The daemon itself can't run anything in a shared folder: its sandbox never gives a shared folder the right to execute (`sandbox.rs`), and on Linux Landlock also forbids the mounts a sandbox for a command needs. So the confined worker asks the process above it, the supervisor, which isn't confined, to start the command in a sandbox of its own, made for that one run with [MXC](https://github.com/crmne/microsoft-mxc) (Bubblewrap on Linux, Seatbelt on macOS; see [Landlock](#landlock) for Linux computers where Bubblewrap can't run, and [Windows](#windows) for Windows):

- It **reads** the system (`/usr`, `/bin`, `/etc` and the rest of what Bubblewrap binds by default) and the language toolchains that exist here: mise (`~/.local/share/mise`, its config in `~/.config/mise`), rbenv, pyenv, rustup, `~/.cargo/bin` (never the rest of Cargo's home, which holds registry credentials), Volta, Bun, Deno, `~/.local/bin`, Nix, Homebrew, `/usr/local` and `/opt`, and the system's C and C++ headers (`/usr/include`, which Bubblewrap's defaults leave out), so builds that compile C work. Never the rest of your home folder: no `~/.ssh`, no browser profiles, no other projects.
- It **writes** only its folder, and a home and temporary folder of its own (`<data>/runs/<id>`, removed when it ends).
- It reaches **this computer's own services** and nothing else, unless the folder says otherwise ([Its network](#its-network)): its databases, caches and development servers, in Docker or not, never the local network or the internet. Each folder's Network is "None", "Local services" (the default) or "Local services and the internet". On Landlock and Windows there are no local services ([Its network](#its-network)).
- It reads **nothing on its standard input**, which ends at once.
- It gets a **clean environment**: `PATH` from the toolchains above and the system, `HOME`, `TMPDIR` and, on Linux and macOS, `XDG_RUNTIME_DIR` (`run`, private to it, since the person's own `/run/user/<uid>` is out of its reach) in its own folder, `LANG=C.UTF-8`, `TERM=dumb`, and what the toolchains need to find themselves (`MISE_INSTALLS_DIR`, `RUSTUP_HOME`, ...). Never the daemon's variables or tokens. mise trusts the folder's own `mise.toml`. Its data, shims, cache and state live in the run's private home: executing an installed tool may create command-wrapper files and locks. `MISE_INSTALLS_DIR`, `MISE_INSTALL_STORE_DIR` and `MISE_PLUGINS_DIR` still point to the read-only host installations and plugins; no host toolchain directory becomes writable. A bot's command in a folder whose loan gives it Claude Code also gets `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_TMPDIR` (its own temporary folder, since Claude Code otherwise writes under `/tmp`, which Seatbelt doesn't give a run), reads the folder Claude Code's program is in, finds that `claude` first on its `PATH`, and reads and writes this computer's own Claude Code sign-in: `~/.claude` and `~/.claude.json`, linked from its home (on Windows only the `.claude` folder, which `CLAUDE_CONFIG_DIR` names, since a process container grants folders only), and on macOS the login keychain. Nothing else of the home folder. The text of the tokens Desktop can read there is taken out of what it prints ([coding-computers.md](coding-computers.md#claude-codes-sign-in)). A folder with repositories set up by `cww coding` also reads their mirrors, in Desktop's data folder. A folder with an environment (`cww roots env`) adds its variables last, each value worked out in the run's own sandbox when it starts and taken out of what it prints ([secrets.md](secrets.md)).
- It has **limits**: memory (4 GB by default; on Linux for the whole command, everything it starts together, and on Windows for each process), at most 256 processes at once, a wall clock (30 minutes), low priority, and at most as many commands at once as the computer has CPUs; CPU time per process is off by default (a build or test suite on many cores spends ten minutes of it in one, all its threads counting), and 0 turns off any of them but the wall clock, which is at least a second. A command over the number at once is refused with `busy`, saying how many run, and the caller can wait for one to end. 0.13.1 and earlier set 600 CPU seconds and 4 commands, and `config.toml` holds every limit, so those exact values always read as the old defaults and move to the new ones: to choose such a limit yourself, use another number, such as 5 commands. They're `command_cpu_seconds`, `command_memory_mb`, `command_processes`, `command_timeout_seconds` and `commands_running` under `[limits]` in `config.toml`. MXC enforces CPU time (an rlimit) and the clock; it limits processes only on Windows, so on Linux whoever runs the command counts the sandbox's processes in `/proc` four times a second and stops it past the limit. On Linux, memory is what the command really uses, swap included, held by a cgroup of its own (`memory.max`), never an rlimit: `RLIMIT_AS` and `RLIMIT_DATA` count address space a program reserves, and rustc and LLVM, a JVM, Go and V8 reserve far more than they use, so they failed to allocate under a 4 GB rlimit with a fraction of it in use. The cgroup needs one systemd delegated (`Delegate=yes`, which the packaged `cww.service` and the unit `cww daemon install` writes have): the first command moves the service's own processes into a leaf, `cww-daemon`, and each command gets `run-<id>` beside it, joined by the sandbox before the command starts (MXC's `resources.cgroup`) and removed, with anything left in it, when it ends. Reaching the limit ends the whole command (`memory.oom.group`), which says so. Where there's no delegated cgroup (`cww daemon run` from a terminal, a container), Linux commands have no memory limit, and the daemon logs it once. On macOS only CPU time, the clock, priority and the number of commands hold: Seatbelt can't hold a memory limit (macOS doesn't enforce memory rlimits, and MXC refuses one there), and nothing counts a run's processes yet, so a Mac sends `memory_mb` and `processes` as 0 and the approval card leaves them out. A run ended by a limit says which (`limit`: `cpu_time`, `processes` or `memory`).

Commands stop when the computer is paused (and none start until it's resumed), and when Chat with Work revokes it.

### Linux command dependencies

Arch, DEB and RPM packages install Bubblewrap, slirp4netns, util-linux (`unshare` and `nsenter`) and iptables. The iptables and ip6tables commands must use the nftables backend; a manually selected legacy backend remains unsupported and is refused. Archive, Homebrew and Nix installs need these tools installed separately and available on the background service's `PATH`. This does not turn on commands or their network setting.

### Landlock

Bubblewrap needs unprivileged user namespaces. Some Linux computers block them: Ubuntu 23.10 and later restrict them with AppArmor, `user.max_user_namespaces` can be 0, and containers filter them. There a command runs on Landlock instead, the kernel's own sandbox, which needs no namespaces, from Linux 6.2. Every run asks MXC for its own choice (`process`), which is Bubblewrap where it can create a sandbox and Landlock otherwise, and the supervisor checks first which one this computer gets. Where neither can run, the command fails at once and says why each can't (Bubblewrap blocked, Landlock missing or older than its ABI 3).

The same rules hold, with these differences:

- **No network, local services included.** Landlock can't tell one address from another, so it could only give a command this computer's whole network, its local servers (a database, a development server, anything listening on `localhost`) and connections in included. So a folder's local services give nothing there, and in a folder that allows the internet, a command fails at once and says so: turn the internet off for that folder, or allow unprivileged user namespaces so Bubblewrap can give it a network of its own.
- **No metadata changes by name.** Landlock decides who reads, writes and runs files, not who changes their permissions, owner or timestamps, so MXC refuses those changes by path (`Operation not permitted`), even in the folder: `chmod +x script.sh` fails, and so does `touch` of a file the command may only read. Changes through a file it opened still work, so `touch` of a file in the folder, or a new one, works, and programs that set a file's mode when they create it (compilers, `install`) work too. A command can still see whether a path outside its folder exists.
- **No private `/dev/shm`**, so POSIX semaphores, and Python's `multiprocessing` locks with them, fail with `Permission denied`.
- A toolchain inside the shared folder (sharing the home folder, with `~/.cargo/bin` in it) is writable like the rest of the folder, rather than read-only inside it.

### Windows

The daemon has no sandbox of its own on Windows yet (`sandbox.rs`), so it starts each command itself, after the checks the supervisor makes elsewhere (below), in a process container made for that one run with MXC: the sandbox Windows gives apps (a BaseContainer), from Windows 11 24H2 and 25H2 with the August 2026 update (builds 26100.9278 and 26200.9278), and 26H2 and 26H1 from their September updates. Windows itself holds the run to what it's granted, without changing the permissions of anyone's files. Where Windows has no BaseContainer, MXC would use an AppContainer instead, which adds entries to the access lists of the folders it grants (the shared folder, the toolchains) for the length of each run. The daemon refuses that (`fallback.allowDaclMutation: false`), so such a computer runs no commands, and the app, `cww status` and allowing commands say why.

The rules are the same, with these differences:

- It **reads** what Windows lets every sandboxed app read (`C:\Windows`, and the programs in `C:\Program Files` whose installer kept that folder's permissions), the folders on the system's `PATH` (the machine's, never your own, and never a whole drive, anyone's profile, or a folder that holds the shared one), and the toolchains installed for you: rustup and `~\.cargo\bin` (never the rest of Cargo's home), mise, Python from python.org and pip's user installs, Git for Windows installed for you, npm's global programs, pnpm, Volta, nvm-windows, Bun, Deno, .NET tools, Scoop, and WinGet's links. Never the rest of your profile, other people's, or other drives.
- It **writes** only its folder and a home of its own (`%LOCALAPPDATA%\cww\data\runs\<id>`, removed when it ends), where `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `TEMP` and `TMP` point.
- It runs in **Windows PowerShell 5.1**, which every Windows has. The command line goes in `command.ps1` in its home, between lines that make its output UTF-8 and its exit code the last command's (PowerShell itself says only 0 or 1), and PowerShell runs it as a script block read from that file, so the command line's quoting and the execution policy don't change it. This PowerShell has no `&&` or `||`: commands are separated with `;`, and `cmd /c` runs cmd syntax. The `run` tool's description says so. Its environment is the system's variables (`SystemRoot`, `ProgramFiles`, `PATHEXT`...), `PSModulePath` naming Windows PowerShell's own modules and those installed for everyone (where most of its commands live) and `PSModuleAnalysisCachePath` keeping PowerShell's module cache in the run's home (left to itself, PowerShell saves it in the folder the command runs in), the toolchains' (`RUSTUP_HOME`, `MISE_INSTALLS_DIR`...), `PYTHONUTF8=1` so Python writes UTF-8, and `npm_config_update_notifier=false` and `NO_UPDATE_NOTIFIER=1`, since without a network npm waits minutes for news of itself before it exits.
- It has **no network** unless the folder allows the internet, and then it reaches the internet and the local network, never this computer's own servers (`localhost`): a process container can't reach them without a loopback exemption only an administrator can add, so a folder's local services give nothing on Windows. Without the internet, names don't resolve and connections are refused at once.
- Windows holds **all its limits** on the container: CPU time and memory for each process, the number of processes at once (a process past it can't start: "Not enough quota is available to process this command"), low priority. A run that failed after it ran into the process or memory limit says which (`limit`: `processes` or `memory`). Stopping a run, or its clock running out, ends everything it started.
- It may use **the Windows UI subsystem**, which PowerShell, Git and most programs load to start, held to itself: no clipboard, no other program's windows, no synthetic input, no new desktops, no system settings, no input methods.
- It needs **a desktop session**: the daemon starts at your sign-in, in your session, and runs commands there. From a service or an SSH session (session 0) PowerShell can't start in a sandbox, so a daemon there runs none and says why.

Windows gives sandboxed apps nothing at the top of a drive, and some programs look at it before anything else: Node.js finds where a script really is from the top down, so `node script.js` and `npm test` fail with `EPERM: operation not permitted, lstat 'C:\'`, and cmd's `dir` and `> NUL` fail too. A process container can be given a folder only with everything in it, so the one way to let them see the top alone is two entries on the drive's permissions that let every sandboxed app read the top folder's own details, never list it or read what's in it: `(RA,REA,RC,S)` for ALL APPLICATION PACKAGES and ALL RESTRICTED APPLICATION PACKAGES, as MXC's `wxc-host-prep prepare-system-drive` adds them. Only an administrator can add them, once per drive: `cww roots prepare-commands`, or **Allow…** under the folders in the app, which asks Windows for one, for the system's drive and the drives of the folders that allow commands. The app and `cww status` say which drives aren't ready. Until then, PowerShell, Git, Python and most programs run; Node.js scripts and those two cmd features don't. To take the entries back, run `icacls C:\ /remove:g *S-1-15-2-1 *S-1-15-2-2` as an administrator.

### Who checks what

The worker names the folder by its ID and the working folder by a path relative to it, never an absolute path. The supervisor reads `config.toml` again for every command, checks that the folder allows commands, and resolves the working folder itself, refusing one that leads outside. A folder that stops allowing commands stops the commands running in it; a worker that ends (to restart under new rules, or because the daemon stops) stops all of its own, and the supervisor waits for them before it goes on.

They talk over a socket pair the worker inherits as a file descriptor (`CWW_RUN_CHANNEL`), one JSON line each way per call (`commands::channel`). A daemon that runs unconfined (the sandbox off, the tests, and Windows) starts commands itself, with the same checks.

On Linux the systemd unit delegates its cgroup (`Delegate=yes`), for commands' memory limits, and preserves read-only system directories (`ProtectSystem=full`), no new privileges, a private temporary directory, and a syscall allowlist. It permits Bubblewrap's four mount operations and `AF_NETLINK` for its isolated loopback setup. A whole-filesystem read-only mount would also make explicitly shared writable folders read-only inside a command, so the confined worker and each command's separate MXC policy enforce the exact folder grants. The unit does not inherit `MemoryDenyWriteExecute` into JIT runtimes or the bundled browser engine, and does not set `RestrictSUIDSGID`, whose separate filter blocks the `openat2` path-resolution call Bubblewrap needs. `NoNewPrivileges` remains enabled. These choices do not enable commands, network access, new roots, or writes in a read-only root.

`cargo test -p cww --test systemd_commands -- --ignored --nocapture` checks the actual packaged unit in a temporary user service: Node, an allowed-folder write, adjacent private-file refusals, clean environment, command network setup, and the daemon's Landlock boundary. The Node fixture disables the separate per-command virtual-memory cap so it tests JIT policy independently; normal command memory limits are unchanged. It needs an active systemd user session, Bubblewrap, slirp4netns and Node. It never changes or restarts the installed daemon.

## What Chat with Work sees

`roots` says which folders allow commands (`allows_commands`), whether they reach the internet (`network`), and how far they reach (`network_access`: `none`, `local` or `internet`). While one does, four more tools are offered:

- `run` starts a command and waits up to 15 seconds for it (Chat with Work waits 20 for a tool call), reporting what it prints as MCP progress notifications (bytes so far, and its latest line). It answers with the exit code and the end of each stream (20 000 characters by default); a longer command keeps running and the answer says so. `background: true` answers at once, for a server or a watcher. `dry_run: true` says where and how it would run, with the folder's network (`network_access`) and the limits, for the approval card, and runs nothing. A result says what the sandbox refused the command, when it did (`blocked`, [What the result says](#what-the-result-says)).
- `run_status` and `run_output` follow a command left running: how it stands, and what it printed from an offset (the latest megabyte is kept).
- `run_stop` stops one, and everything it started.

`run` is annotated destructive and open-world, so Chat with Work asks for each one, unless the chat runs under "Allow everything" ([Who approves](#who-approves)); `run_stop` is a plain write; the other two only read. Each call is in the activity log with how it ended and the command line ("exit 0 · bin/rails test"). That log stays on this computer.

## Who approves

Every command has an approval, decided in Chat with Work: on the web or in any of its apps, never on this computer. When the person chose "Allow everything" as their permission mode in a chat, Chat with Work runs that chat's commands without a card, as it already does for file changes there, and still records each one. Guests, scheduled and event runs, and bots' and agents' chats always ask (a bot's unattended loan, which only the person here turns on, aside: [PROTOCOL.md 7.2.1](../PROTOCOL.md#721-bots)).

What this computer decides is where commands may run at all: per folder, commands allowed or not, and how far they reach ([Its network](#its-network)), which only the person on the computer turns on. There is no allowlist of command lines. The daemon can't tell an approval from a forged one, or from a chat that allows everything, so in a folder that allows commands, a compromised server could run commands without anyone approving them; the sandbox, the limits and the audit log hold either way.

## On this computer

The desktop app's chat page and `cww tui` list the commands running here (and the last few to end) under the conversation, from the daemon itself ([CONTROL.md, `commands`](../CONTROL.md#commands-command_output-and-command_stop)), never from the server: each with its command line, folder, how long it has run and how it ended. In the app, a line over the composer says what runs, where and for how long, with Stop and Show output, which lists them with what the chosen one prints as it prints it (escape sequences and progress-bar redraws cleaned out). In the terminal, the same line sits over the composer, and `/commands` opens the list: ↑↓ choose, `s` stops, Esc closes. Stopping is written to the activity log (`command_stopped`).

## What it doesn't protect against

- **A command can change or delete anything in its folder**, and nothing in the trash brings that back: allow commands, and approve each one or allow everything in a chat, knowing that. Version control is the undo.
- **A compromised server could run commands** in folders that allow them, without anyone approving them ([Who approves](#who-approves)).
- **A command reads everything in its folder**, the deny list included (`.env`, keys): the deny list keeps files from Chat with Work's tools, not from programs run in the folder.
- **A command's output can say where its folder is on this computer.** Chat with Work's tools name folders by their labels, but programs print paths: `pwd`, error messages and stack traces everywhere, and on Windows PowerShell's `dir` shows `Directory: C:\Users\you\project` above its listing. The output reaches Chat with Work as the command printed it.
- **A bot's command given Claude Code's sign-in reads and writes Claude Code's own files**: its tokens (refresh token included), its history, and its settings, where a hook or MCP server it leaves runs when you next start `claude` yourself, outside any sandbox. On macOS it reaches the login keychain as Claude Code does. Only bots you said yes for on this computer get it ([coding-computers.md](coding-computers.md#claude-codes-sign-in)).
- **Toolchain settings are readable**, and so is wherever a toolchain's folder links to (a `~/.config/mise` that links to your dotfiles reads all of them): mise's config can hold environment variables, and on Windows so can npm's global settings (`%APPDATA%\npm\etc\npmrc`), which npm keeps beside its global programs.
- **The process limit is a count, not a wall.** On Linux it's checked four times a second, so a fork bomb can make many processes in between before it's stopped (the user's own `ulimit -u` still applies). On Linux a parallel build's processes share the command's memory limit: raise `command_memory_mb` where a big build needs more than 4 GB at once. On macOS there's none yet, and no memory limit either: only CPU time per process where `command_cpu_seconds` sets one (none by default), and the wall clock, end the rest. On Windows the container holds it.
- **Local services are this computer's services, as they are.** A database on this computer that needs no password (PostgreSQL with `trust`, Redis without `requirepass`, a MongoDB or Elasticsearch with no users) is a command's to read and change, whichever project it belongs to, and so is any admin interface listening locally: a container's, a local Kubernetes API, a home-made one. This computer's SSH server is a service too: a command can reach it, though not with your keys, which it can't read. Desktop leaves out the ports that would let a command out of its sandbox ([What it reaches, and what it never does](#what-it-reaches-and-what-it-never-does)), not every service that holds data. Turn local services off for a folder ("None") where that matters, or give your local services passwords.
- **The internet, when allowed, is the whole internet** and the whole local network. Allowing it per host isn't built; exact local-network addresses are. On Bubblewrap, local services and the internet need `slirp4netns` and the other tools MXC lists; without them, a command in such a folder fails to start and says why. On [Landlock](#landlock) there's no network at all. On Windows it's the internet and the local network, but never this computer's own servers.
- **A name lookup can say a little.** Without the internet, a lookup is refused before it leaves this computer, but the name the command asked for reaches Desktop's log of what was refused, and the result.
- **On Windows, a command can show windows of its own** on your desktop, though it can't read or drive other programs' windows, the clipboard or your input. And the daemon that starts it isn't sandboxed there yet: the command is, and the daemon checks the folder and the working folder itself, as everywhere.
- **Custom systemd restrictions also apply to commands.** A local override that denies JIT memory, mount syscalls, `openat2` or writes to the chosen root can prevent commands from starting. The shipped unit supports those operations; the worker and each command still have their own sandbox.
