# Running commands

Status: **built on Linux, tested on macOS and Windows.** On macOS, commands were tried for real on 2026-10-27 on a Mac mini (Apple silicon, macOS 27) paired with staging: approved runs, a failing one, the network off and on, the CPU limit, a background run with its output followed in `cww tui` and stopped from there and from a chat, and the sandbox refusing to read or write outside its folder. Up to 0.6.2 every command on a Mac failed to start ("resources.memoryMb is not supported by the 'seatbelt' backend"); the tests ran with the fix that followed. On Windows, commands run from Windows 11 24H2 with the August 2026 update ([Windows](#windows)); the tests that run them for real passed on 2026-10-27 on a Windows 11 26H2 virtual machine, in a standard user's desktop session, and on Windows 11 on Arm (25H2) in CI. The same day, on that virtual machine, the installer CI built, paired with staging as a standard user, ran `dir`, `git status` and `npm test`, a failing build, a background run followed in `cww tui` and stopped from a chat, a command approved in `cww tui`, and a read outside its folder that the sandbox refused. In a shared folder that allows changes, you can also allow commands. Chat with Work can then run one line of shell there (Windows PowerShell on Windows), like `bin/rails test` or `npm run build`, each after you approve it. The wire details are in [PROTOCOL.md, section 8.15](../PROTOCOL.md#815-commands), and the switch in [CONTROL.md, `roots_commands`](../CONTROL.md#roots_commands).

## Where a command runs

The daemon itself can't run anything in a shared folder: its sandbox never gives a shared folder the right to execute (`sandbox.rs`), and on Linux Landlock also forbids the mounts a sandbox for a command needs. So the confined worker asks the process above it, the supervisor, which isn't confined, to start the command in a sandbox of its own, made for that one run with [MXC](https://github.com/crmne/microsoft-mxc) (Bubblewrap on Linux, Seatbelt on macOS; see [Landlock](#landlock) for Linux computers where Bubblewrap can't run, and [Windows](#windows) for Windows):

- It **reads** the system (`/usr`, `/bin`, `/etc` and the rest of what Bubblewrap binds by default) and the language toolchains that exist here: mise (`~/.local/share/mise`, its config in `~/.config/mise`), rbenv, pyenv, rustup, `~/.cargo/bin` (never the rest of Cargo's home, which holds registry credentials), Volta, Bun, Deno, `~/.local/bin`, Nix, Homebrew, `/usr/local` and `/opt`. Never the rest of your home folder: no `~/.ssh`, no browser profiles, no other projects.
- It **writes** only its folder, and a home and temporary folder of its own (`<data>/runs/<id>`, removed when it ends).
- It has **no network**, unless the folder allows it ("Commands use the network"). Without it, the system resolver's socket is hidden too. On Landlock it can't open a network socket at all.
- It gets a **clean environment**: `PATH` from the toolchains above and the system, `HOME` and `TMPDIR` in its own folder, `LANG=C.UTF-8`, `TERM=dumb`, and what the toolchains need to find themselves (`MISE_DATA_DIR`, `RUSTUP_HOME`, ...). Never the daemon's variables or tokens. mise trusts the folder's own `mise.toml`.
- It has **limits**: CPU time and memory for each process it starts (600 CPU seconds and 4 GB by default), at most 256 processes at once, a wall clock (30 minutes), low priority, and at most 4 commands at once. They're `command_cpu_seconds`, `command_memory_mb`, `command_processes`, `command_timeout_seconds` and `commands_running` under `[limits]` in `config.toml`. MXC enforces CPU time and memory (rlimits) and the clock; it limits processes only on Windows, so on Linux whoever runs the command counts the sandbox's processes in `/proc` four times a second and stops it past the limit. On macOS only CPU time, the clock, priority and the number of commands hold: Seatbelt can't hold a memory limit (macOS doesn't enforce `RLIMIT_AS`, and MXC refuses one there), and nothing counts a run's processes yet, so a Mac sends `memory_mb` and `processes` as 0 and the approval card leaves them out. A run ended by a limit says which (`limit`: `cpu_time` or `processes`, and on Windows `memory`).

Commands stop when the computer is paused (and none start until it's resumed), and when Chat with Work revokes it.

### Landlock

Bubblewrap needs unprivileged user namespaces. Some Linux computers block them: Ubuntu 23.10 and later restrict them with AppArmor, `user.max_user_namespaces` can be 0, and containers filter them. There a command runs on Landlock instead, the kernel's own sandbox, which needs no namespaces, from Linux 6.2. Every run asks MXC for its own choice (`process`), which is Bubblewrap where it can create a sandbox and Landlock otherwise, and the supervisor checks first which one this computer gets. Where neither can run, the command fails at once and says why each can't (Bubblewrap blocked, Landlock missing or older than its ABI 3).

The same rules hold, with these differences:

- **No network.** Landlock can't tell one address from another, so it could only give a command this computer's whole network, its local servers (a database, a development server, anything listening on `localhost`) and connections in included. So in a folder that allows the network, a command fails at once and says so: turn the network off for that folder, or allow unprivileged user namespaces so Bubblewrap can give it a network of its own.
- **No metadata changes by name.** Landlock decides who reads, writes and runs files, not who changes their permissions, owner or timestamps, so MXC refuses those changes by path (`Operation not permitted`), even in the folder: `chmod +x script.sh` fails, and so does `touch` of a file the command may only read. Changes through a file it opened still work, so `touch` of a file in the folder, or a new one, works, and programs that set a file's mode when they create it (compilers, `install`) work too. A command can still see whether a path outside its folder exists.
- **No private `/dev/shm`**, so POSIX semaphores, and Python's `multiprocessing` locks with them, fail with `Permission denied`.
- A toolchain inside the shared folder (sharing the home folder, with `~/.cargo/bin` in it) is writable like the rest of the folder, rather than read-only inside it.

### Windows

The daemon has no sandbox of its own on Windows yet (`sandbox.rs`), so it starts each command itself, after the checks the supervisor makes elsewhere (below), in a process container made for that one run with MXC: the sandbox Windows gives apps (a BaseContainer), from Windows 11 24H2 with the August 2026 update (builds 26100.9278 and 26200.9278, and 26H2 and 26H1 from their September updates). Windows itself holds the run to what it's granted, without changing the permissions of anyone's files. Where Windows has no BaseContainer, MXC would use an AppContainer instead, which adds entries to the access lists of the folders it grants (the shared folder, the toolchains) for the length of each run. The daemon refuses that (`fallback.allowDaclMutation: false`), so such a computer runs no commands, and the app, `cww status` and allowing commands say why.

The rules are the same, with these differences:

- It **reads** what Windows lets every sandboxed app read (`C:\Windows`, and the programs in `C:\Program Files` whose installer kept that folder's permissions), the folders on the system's `PATH` (the machine's, never your own, and never a whole drive, anyone's profile, or a folder that holds the shared one), and the toolchains installed for you: rustup and `~\.cargo\bin` (never the rest of Cargo's home), mise, Python from python.org and pip's user installs, Git for Windows installed for you, npm's global programs, pnpm, Volta, nvm-windows, Bun, Deno, .NET tools, Scoop, and WinGet's links. Never the rest of your profile, other people's, or other drives.
- It **writes** only its folder and a home of its own (`%LOCALAPPDATA%\cww\data\runs\<id>`, removed when it ends), where `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `TEMP` and `TMP` point.
- It runs in **Windows PowerShell 5.1**, which every Windows has. The command line goes in `command.ps1` in its home, between lines that make its output UTF-8 and its exit code the last command's (PowerShell itself says only 0 or 1), and PowerShell runs it as a script block read from that file, so the command line's quoting and the execution policy don't change it. This PowerShell has no `&&` or `||`: commands are separated with `;`, and `cmd /c` runs cmd syntax. The `run` tool's description says so. Its environment is the system's variables (`SystemRoot`, `ProgramFiles`, `PATHEXT`...), `PSModulePath` naming Windows PowerShell's own modules and those installed for everyone (where most of its commands live) and `PSModuleAnalysisCachePath` keeping PowerShell's module cache in the run's home (left to itself, PowerShell saves it in the folder the command runs in), the toolchains' (`RUSTUP_HOME`, `MISE_DATA_DIR`...), `PYTHONUTF8=1` so Python writes UTF-8, and `npm_config_update_notifier=false` and `NO_UPDATE_NOTIFIER=1`, since without a network npm waits minutes for news of itself before it exits.
- It has **no network** unless the folder allows it, and then it reaches the internet and the local network, never this computer's own servers (`localhost`). Without it, names don't resolve and connections are refused at once.
- Windows holds **all its limits** on the container: CPU time and memory for each process, the number of processes at once (a process past it can't start: "Not enough quota is available to process this command"), low priority. A run that failed after it ran into the process or memory limit says which (`limit`: `processes` or `memory`). Stopping a run, or its clock running out, ends everything it started.
- It may use **the Windows UI subsystem**, which PowerShell, Git and most programs load to start, held to itself: no clipboard, no other program's windows, no synthetic input, no new desktops, no system settings, no input methods.
- It needs **a desktop session**: the daemon starts at your sign-in, in your session, and runs commands there. From a service or an SSH session (session 0) PowerShell can't start in a sandbox, so a daemon there runs none and says why.

Windows gives sandboxed apps nothing at the top of a drive, and some programs look at it before anything else: Node.js finds where a script really is from the top down, so `node script.js` and `npm test` fail with `EPERM: operation not permitted, lstat 'C:\'`, and cmd's `dir` and `> NUL` fail too. A process container can be given a folder only with everything in it, so the one way to let them see the top alone is two entries on the drive's permissions that let every sandboxed app read the top folder's own details, never list it or read what's in it: `(RA,REA,RC,S)` for ALL APPLICATION PACKAGES and ALL RESTRICTED APPLICATION PACKAGES, as MXC's `wxc-host-prep prepare-system-drive` adds them. Only an administrator can add them, once per drive: `cww roots prepare-commands`, or **Allow…** under the folders in the app, which asks Windows for one, for the system's drive and the drives of the folders that allow commands. The app and `cww status` say which drives aren't ready. Until then, PowerShell, Git, Python and most programs run; Node.js scripts and those two cmd features don't. To take the entries back, run `icacls C:\ /remove:g *S-1-15-2-1 *S-1-15-2-2` as an administrator.

### Who checks what

The worker names the folder by its ID and the working folder by a path relative to it, never an absolute path. The supervisor reads `config.toml` again for every command, checks that the folder allows commands, and resolves the working folder itself, refusing one that leads outside. A folder that stops allowing commands stops the commands running in it; a worker that ends (to restart under new rules, or because the daemon stops) stops all of its own, and the supervisor waits for them before it goes on.

They talk over a socket pair the worker inherits as a file descriptor (`CWW_RUN_CHANNEL`), one JSON line each way per call (`commands::channel`). A daemon that runs unconfined (the sandbox off, the tests, and Windows) starts commands itself, with the same checks.

## What Chat with Work sees

`roots` says which folders allow commands (`allows_commands`) and whether they may use the network. While one does, four more tools are offered:

- `run` starts a command and waits up to 15 seconds for it (Chat with Work waits 20 for a tool call), reporting what it prints as MCP progress notifications (bytes so far, and its latest line). It answers with the exit code and the end of each stream (20 000 characters by default); a longer command keeps running and the answer says so. `background: true` answers at once, for a server or a watcher. `dry_run: true` says where and how it would run, with the folder's network setting and the limits, for the approval card, and runs nothing.
- `run_status` and `run_output` follow a command left running: how it stands, and what it printed from an offset (the latest megabyte is kept).
- `run_stop` stops one, and everything it started.

`run` is annotated destructive and open-world, so Chat with Work asks every time; `run_stop` is a plain write; the other two only read. Each call is in the activity log with how it ended and the command line ("exit 0 · bin/rails test"). That log stays on this computer.

## On this computer

The desktop app's chat page and `cww tui` list the commands running here (and the last few to end) under the conversation, from the daemon itself ([CONTROL.md, `commands`](../CONTROL.md#commands-command_output-and-command_stop)), never from the server: each with its command line, folder, how long it has run and how it ended. In the app, a line over the composer says what runs, where and for how long, with Stop and Show output, which lists them with what the chosen one prints as it prints it (escape sequences and progress-bar redraws cleaned out). In the terminal, the same line sits over the composer, and `/commands` opens the list: ↑↓ choose, `s` stops, Esc closes. Stopping is written to the activity log (`command_stopped`).

## What it doesn't protect against

- **A command can change or delete anything in its folder**, and nothing in the trash brings that back: approve each one knowing that. Version control is the undo.
- **A command reads everything in its folder**, the deny list included (`.env`, keys): the deny list keeps files from Chat with Work's tools, not from programs run in the folder.
- **Toolchain settings are readable**: mise's config can hold environment variables, and on Windows so can npm's global settings (`%APPDATA%\npm\etc\npmrc`), which npm keeps beside its global programs.
- **The process limit is a count, not a wall.** On Linux it's checked four times a second, so a fork bomb can make many processes in between before it's stopped (the user's own `ulimit -u` still applies). On macOS there's none yet, and no memory limit either: CPU time is limited per process, and the wall clock ends the rest. On Windows the container holds it.
- **The network, when allowed, is the whole network.** Allowing it per host isn't built. On Bubblewrap it needs `slirp4netns` and the other tools MXC lists; without them, a command in a folder that allows the network fails to start and says why. On [Landlock](#landlock) there's no network at all. On Windows it's the internet and the local network, but never this computer's own servers.
- **On Windows, a command can show windows of its own** on your desktop, though it can't read or drive other programs' windows, the clipboard or your input. And the daemon that starts it isn't sandboxed there yet: the command is, and the daemon checks the folder and the working folder itself, as everywhere.
- **The systemd unit's own limits apply to commands.** The supervisor runs under `cww daemon install`'s unit, whose `MemoryDenyWriteExecute`, system call filter and `ProtectSystem=strict` carry over to everything it starts: JIT runtimes (Node, the JVM) may fail there until the unit is relaxed for them.

## Not built yet

- Windows without a BaseContainer (Windows 10, and Windows 11 before 24H2 or its August 2026 update): commands stay off there, rather than run in an AppContainer that changes the permissions of the folders it grants.
- Live output inside the chat's step: the step shows the result when the call answers, and the server would have to pass progress through the chat API for more. Until then this computer's windows show it themselves (below).
