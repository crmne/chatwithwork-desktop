# Chat with Work Desktop

`cww-app` is the desktop app: the Chat with Work web app in a window of its own, the tray item for the `cww` daemon, and the background agent's settings. It lives in `app/` and is built with [Tauri 2](https://tauri.app) on the system's web view: WebKitGTK 4.1 on Linux, WKWebView on macOS, WebView2 on Windows. The daemon doesn't need it: servers and people who prefer the command line keep using `cww` and `cww tui`.

Until 0.3.1 the app was native, drawn with egui, with a chat window of its own that had to follow every change to the web app. That code is kept at the [`egui-final`](https://github.com/crmne/chatwithwork-desktop/tree/egui-final) tag, with its docs (`docs/settings-app.md`, `docs/chat-window.md`, `docs/native-parity.md`). The prototype and measurements that led here are kept at the [`tauri-prototype-final`](https://github.com/crmne/chatwithwork-desktop/blob/tauri-prototype-final/docs/tauri-prototype.md) tag.

## The parts

| | What | Talks to |
|---|---|---|
| **Chat with Work window** (`main`, and `page-N` for pages it opens in a new window) | The real web app, loaded from the server | The server, like a browser. The app only through the bridge below |
| **Computer settings pane** (`computer-pane-main`, or `computer-pane-page-N`) | App-owned child webview in the same window: General, Shared folders, Browser, Notifications, Account, Activity | The daemon through `local.rs`, never the remote DOM |
| **Scan window** (`scan`) | A bundled page (`app/ui/scan.html`): scan, check the pages, send them ([scanning.md](scanning.md)) | The scanner through a helper process (`--scan-helper`), and the daemon only to send, through `scan.rs`'s own commands |
| **Tray item** | The daemon's state (and a second line only while there is more to say), Open Chat with Work, Scan…, Pause Sharing, Settings, Quit | The daemon's status, followed by one thread |

While no window is open the app is its tray item and that thread: a window's web view, and on Linux and macOS its web processes, go with the window. Closing the last window never quits; Quit in the tray or in General does. On macOS the app has a Dock icon only while a window is open.

The same binary is also pipe-only helpers, started before any window or tray exists: the daemon and `cww tui` start `--notification-broker` (native notifications, through fastframe-notifications in `notification-broker/`), `--record-audio` / `--record-audio-progress` (the terminal composer's microphone, through fastframe-audio), and `--transcribe-local <model>` (Whisper on this computer); the app itself starts `--scan-helper` (the scanner's driver, while the scan window is open). They keep the name `cww-app`, so the daemon, `cww tui`, the packages and existing start-at-login entries find them where they were.

## The Chat with Work window

- **Which server.** The server this computer is paired with (`config.toml`'s `server.url`), so staging and self-hosted installs open their own site; chatwithwork.com before pairing; `--server <url>` for development (plain `http` only on localhost). When the computer is paired with another server, the window follows.
- **Where it opens.** `/chats/new`, which leads into the organization used last, as the installed web app does. A notification's chat (`--open-chat`, as the daemon starts it) opens at `/<account>/chats/<number>`, only on that same server.
- **Staying signed in.** Cookies live in the web view's own data directory (`~/.local/share/com.chatwithwork.desktop` on Linux, the app's WebKit store on macOS, `%LOCALAPPDATA%\com.chatwithwork.desktop` on Windows). A web view drops session cookies when the app quits, so the server signs the desktop in with "remember me" (see the server contract).
- **Who it is.** The user agent is the platform web view's plus `(Chat with Work Desktop; platform=linux; version=0.3.1; build=301; bridge-components: [external preferences auth-session downloads computer scan settings-pane-v1])`, in parentheses, as a comment: WebKitGTK refuses a user agent that is not RFC 7231 products and comments (`user_agent.rs`). It never matches the phone apps' `Chat with Work; platform=ios|android`, so the server shows the desktop the web app's full layout.
- **Leaving the server.** Links and `GET` forms to other sites open in the default browser (the bridge script intercepts them before the web view does); `mailto:` opens the mail app; other schemes go nowhere. A page from elsewhere that loads anyway as the window's page (a redirect, a script) is stopped and opened in the browser. Other sites may load in frames, since the web views give the navigation handler only a URL for the page and its frames alike (the MCP Apps sandbox, the support widget and payment forms are frames). `target="_blank"` on the server's own pages opens another app window, which shares the sign-in (`policy.rs`).
- **Signing in with Google, Slack or Dropbox, and connecting services.** Google refuses OAuth in web views, and passkeys don't work there, so these run in the default browser and come back through a loopback callback (RFC 8252): the page asks the bridge to `listen()`, which answers `http://127.0.0.1:<port>/<32 random characters>` for ten minutes; the server sends the browser there at the end with a one-time token, which the page redeems with the PKCE verifier only it holds. Anything else that reads the token can't use it. The browser shows "You can close this tab". See the server contract for the flows.
- **Files.** Dropped on the window, they reach the page as an HTML drop, so the composer takes them as uploads (Tauri's own drop handler is off). Downloads go to the Downloads folder under their own name, never replacing a file there, and the folder is shown.
- **Dictation.** The microphone is allowed for the server's pages only, so the composer's microphone works as on the web (macOS asks once, with the bundle's `NSMicrophoneUsageDescription`). Nothing else is granted to any page.
- **First paint.** New server windows remain hidden until their first trusted page finishes loading, with a five-second fallback so a stalled resource cannot leave the app invisible. Native backing colors match the canvas. The bundled child applies its supplied theme before styles and asynchronous native calls, and loads its document once; tab switches keep that same document.
- **Offline.** When the server can't be reached (a TCP connection to its host and port within four seconds, name lookup included, checked before the window opens or moves to the server, and skipped behind a proxy from config.toml or the environment), the window shows a page bundled in the app instead of the web view's error page: which server, Retry, Open Settings, Open Anyway (for a system proxy the check can't see), and a check of its own every 15 seconds that goes back where the window was headed once the server answers (`offline.rs`, `ui/offline.html`). On Linux a server page that fails to load later is checked the same way; WKWebView and WebView2 don't report failed loads to Tauri, so there the check happens when the window opens or a notification or the settings move it. The page gets three commands of its own (`offline_info`, `offline_retry`, `offline_settings`), through a capability for bundled pages in that webview only.
- **Notifications.** The daemon already shows native notifications, with the window open or closed, with generic text, and the web page tells the server which chat is on screen, so the window adds none of its own. Web Push in the web view isn't used.
- **Shortcuts.** Ctrl+, (Cmd+, on macOS) opens this computer's settings: Chat with Work's Settings, This computer, where the page names it (`<meta name="chatwithwork-desktop-settings">`), else the app-owned settings in that same window; Ctrl and plus or minus zoom.
- **Linux on NVIDIA.** Under Wayland with NVIDIA's driver, WebKitGTK can't draw with explicit sync (the window stays empty or the GPU process dies with protocol error 71), so the app sets `__NV_DISABLE_EXPLICIT_SYNC=1` for itself, only when the driver is loaded and the session is Wayland, and never over a value already set (`linux.rs`).
- **Linux high-refresh displays.** WebKitGTK's GTK 3 GL frame clock can keep animations near 60 fps even on a 120/144 Hz display. On 2026-10-30, a fully hidden 120 Hz Wayland comparison of the same synthetic transform, backdrop-blur and scrolling workloads measured about 60 fps in the actual app (WebKitGTK 2.54.1, GTK 3.24.52, NVIDIA 615.78.08) and 120 fps in Chromium, with no frame above 25 ms in either. NVIDIA rendering was confirmed from the owned WebKit processes, not their privacy-masked WebGL renderer string. Turning off WebKit's `PreferPageRenderingUpdatesNear60FPS` in an isolated view still measured 60 fps; it does not fix the GTK 3 GL clock. This matches [WebKit's upstream GTK investigation](https://bugs.webkit.org/show_bug.cgi?id=199376#c8). Keep GPU rendering and the explicit-sync workaround: forcing CPU copies is not a suitable fix. [WebKitGTK 2.54.2](https://webkitgtk.org/2026/10/23/webkitgtk2.54.2-released.html) separately fixes backdrop-filter performance; that release note does not establish a high-refresh-clock fix. These synthetic measurements isolate the refresh ceiling, not every real page's performance.
- **Without a desktop.** Started where there's no display (over SSH, or with a stale or missing `WAYLAND_DISPLAY` and `DISPLAY`), the app says so in a sentence and exits with an error, instead of panicking in Tauri's event loop (`linux::open_display`). A daemon started as a systemd user service before the desktop session exported its display has none of its own, so when it opens a notification's chat in the app it takes the display from the user manager's current environment (`notification_delivery.rs`); if the app still can't start, the chat opens in the browser.

## The bridge

The web app's pages get these commands, and nothing else Tauri offers (no events, windows, files or shell):

| Command | Page API (`window.ChatWithWorkDesktop`) | Does |
|---|---|---|
| `open_external` | `openExternal(url)` | Opens an `http`, `https` or `mailto` URL in the default app |
| `open_preferences` | `openPreferences(page)` | Opens local settings in the same window (`activity`, `folders`, `general`...) |
| `listen` | `listen()` | Starts the loopback callback; resolves `{ callback }`, and later dispatches `chatwithwork-desktop:callback` with `{ callback, params }` |
| `computer` | `computer.status()` | What the page may see of this computer (below) |
| `computer_change` | `computer.pause()`, `.resume()`, `.removeFolder(id)`, `.renameFolder(id, label)`, `.allowChanges(id, on)`, `.allowCommands(id, on)`, `.allowNetwork(id, on)` | Changes what this computer shares, as below; resolves the new state, or `{ declined: true }` |
| `computer_add_folder` | `computer.addFolder()` | Shares a folder the person picks in the system's folder picker; resolves `{ folder }` (its label, or `null`) |
| `computer_notifications` | `computer.notifications()`, `.allowNotifications()` | Whether native notifications can show here (`permission`, `connected`), and the system's own question to allow them |
| `scan` | `scan()` | Opens the scan window for the page's composer; resolves a PDF `File` once the person attaches what they scanned, or `null` if they close the window |
| `scan_pending` | `pendingScan()` | The scan the person sent to a new chat from the scan window, as a `File`, or `null` |
| `scan_file` | (inside the two above) | The PDF's bytes, once, to the window it was made for: an `ArrayBuffer` through Tauri's IPC protocol, or a plain array of numbers where the page's Content Security Policy makes Tauri fall back to `postMessage` (Chat with Work's pages do), which the bridge turns back into bytes before making the `File` |
| `page_dialog` | (none: Turbo's `data-turbo-confirm`, and `alert()`) | Shows the page's confirmation or alert in the system's message box; resolves whether the person confirmed |

Two checks enforce it. A capability added at start (`desktop.rs`), for the server's origin as a remote URL and the web app's windows only, allows these commands; and each command checks again that its caller is a page of the server in one of those windows (`bridge.rs`). The bridge script (`bridge.js`) defines `window.ChatWithWorkDesktop` only on pages of the server. The user agent's `bridge-components` add `computer` and `scan` for these, so the server shows their controls only to a build that has them.

### Dialogs

The dialog plugin's own script (tauri-plugin-dialog, which the app uses for its questions and pickers) replaces every page's `window.alert()` and `window.confirm()` with calls to its `message` command, which the server's pages may not make, so a `data-turbo-confirm` button did nothing and an alert showed nothing. The bridge script replaces them again, and takes over Turbo's confirmation once Turbo loads (`config.forms.confirm`, or `setConfirmMethod` in Turbo 7): each asks through `page_dialog`, which the app shows in the system's message box over the page's window. It reads the same attributes as the phone apps' `alert` component: `data-bridge-confirm` names the confirm button, `data-bridge-description` adds a line under the message, and a `DELETE` (or `data-bridge-destructive="true"`) shows as a warning with "Delete" unless named. The dialog is titled with the server's host, as a browser's are, so it never reads as one of the app's own questions, and answering it changes nothing on the computer; messages are clipped to 1,000 characters and the button to 32. Only one dialog shows at a time, the app's own questions included: while one is open, another confirmation answers Cancel and another alert is dropped. `window.confirm()` answers a promise of the answer, as the plugin's did, since a native dialog can't answer at once: the web app asks through Turbo's confirmation or awaits it. `window.prompt()` is the web view's own (WKWebView shows none), and the web app doesn't use it.

### This computer

Chat with Work's Settings has a This computer page, and the new chat page's panel for this computer shows its folders, when they run in this app (the server's `docs/desktop-app.md`). What a computer shares and allows is still decided on the computer (the server's `docs/security/desktop.md`): a page of the server is the server's code, so the app treats what it asks as a suggestion (`computer.rs`):

- **Narrowing happens at once**: pausing, stopping sharing a folder, turning changes, commands or their network off. A compromised server could make the computer share less, never more.
- **Widening waits for the person**: resuming, allowing changes, commands, or the network for commands each ask in a dialog the app draws over the window (tauri-plugin-dialog, the system's own message box), which no page can see or answer, naming the folder as the daemon has it, never as the page said. A folder is added only through the system's folder picker, where the person picks it; the page can't name one. One question shows at a time.
- **Pages never see** where a folder is on this computer (`local_path`), the activity log, the deny list, the config file or the proxy, or which bots share a folder (only how many). Those stay in an app-owned child webview inside the same Settings shell. Remote JavaScript receives none of them. The legacy remote folder picker also returns only a label on success and a generic failure; detailed validation stays in local settings. Remote file-tool refusals name neither a matched exclusion nor a protected absolute app directory.
- **The state follows**: each time what a page sees changes, the app dispatches `chatwithwork-desktop:computer` with it on the server's pages in its windows.

`status()` answers `{ running, paired, server, device_id, paused, connection, health: { label, tone }, folders: [{ id, label, available, index, indexed_files, changes, commands, network, bots }], commands }` (`commands`: whether this computer runs commands: everywhere but Windows, and there where the daemon's status says it can, from Windows 11 24H2 with the August 2026 update). The server matches `device_id` with its own row for the computer.

Settings in the tray opens This computer in the Chat with Work window once the computer is paired and that window is signed in (its "remember me" cookie for the server), and the app-owned navigation in that same window otherwise: before pairing, while the agent isn't running, and after pairing before anyone signs in to the window, since approving the computer in the browser signs nobody in there (`windows::show_computer_settings`).

## The settings pages and the daemon

The local pane shows `app/ui`, plain HTML, CSS and JavaScript without a framework or build step, styled with the web app's Live Wire tokens (`ui/tokens.css`, copied from the web app) and Geist. They work without a network and before pairing. Only they reach the daemon:

The welcome page leads with **Open Chat with Work**, which works without
pairing this computer or sharing folders. **Use files from this computer**
expands the optional pairing and folder steps; nothing is shared by opening
the app. Crash reports remain a separate choice. Welcome stays in the
settings navigation until completed, so browsing the other pages doesn't
lose the way back. If opening the chat or saving a preference fails, the
welcome page keeps the choice and shows the error so it can be retried.

- The capability in `capabilities/local.json` names only the app-owned child webviews and no remote URL. Each command in `local.rs` checks its exact webview label and bundled page URL again.
- `control` sends a control request (CONTROL.md) only if it is on `local::ALLOWED`: status, pause and resume, shared folders and their changes and commands, sharing them with bots (`roots_bot`), the deny list, the activity log, and notification permission. Never chats, uploads, `reload` or `shutdown`.
- The rest are the app's own: pairing (it runs `cww login --json` and reports its code and outcome as `pairing` events), the folder picker, starting the daemon (`cww daemon install`), start at login, crash reports, dictation preferences and Whisper models for `cww tui`, opening the config file or the logs, opening the Chat with Work window on one of the server's pages, and on Windows letting commands see the top of the drives they run on (`prepare_command_drives`, which asks Windows for an administrator, over the same application window; [commands.md](commands.md#windows)).
- The daemon's status arrives as a `status` event, which the app hands to the page by calling its `window.cwwEvent` (so the pages need none of Tauri's own APIs, not even its events); the activity log's sentences are made in Rust (`activity.rs`), as the egui app made them.

Organizations, people, notification preferences, models and templates are in the web app's Settings, in the Chat with Work window, and so are this computer's folders, pausing and native notifications (This computer, above), through the bridge rather than this allow-list.

## The scan window

Scan… in the tray, `cww-app --scan`, or the composer's attach menu in the Chat with Work window (the bridge's `scan()`) opens it. Its page gets its own commands (`capabilities/scan.json`, for the `scan` window and no remote URL; each command in `scan.rs` checks its caller again), never the settings' `control`: the scanner goes through a helper process the app starts while the window is open, the daemon is asked only for which bots take scans and to send one to a bot (`scan_destinations`, `scan_send`), a scan for a chat goes to the Chat with Work window's composer (`scan_attach`, then the bridge's `scan_file`), and Save to Computer writes the PDF where the person picks in the system's save dialog, without the daemon. Pages are kept in a private folder under the app's state directory and deleted on Rescan, when the window closes, and when the app starts. The details are in [scanning.md](scanning.md).

## Sharing with bots

Shared folders and Browser list which bots currently use them. The switches live in the bot’s Settings, inside its existing **Use this computer** integration. The app independently resolves that bot through the paired device’s DPoP API before showing or changing a grant. A different account, another person’s device, a guest, a private or inaccessible bot, or an integration for another device cannot mount it. Sharing more requires an OS dialog; stopping sharing takes effect immediately. Unattended commands appear only where the folder allows commands and require a separate confirmation.

The CLI uses `cww roots share <root> <bot> [--unattended]`, `cww roots unshare <root> <bot>`, and `cww browser share|unshare <bot>`. Older command names remain hidden aliases; the local wire fields and audit event names remain compatible.

## Same-window settings contract (`settings-pane-v1`)

**General** comes first in the six **This computer** links, which belong to the web Settings navigation. Shared folders always shows its Run commands switch, disabled with its prerequisite when unavailable, and reports only existing bot access. It ends with an Add folder footer and **Excluded files and folders**, one full-width section for custom exclusions and read-only built-in protections. Custom exclusions can be added, edited or removed here. Adding narrows sharing immediately; editing or removing asks in an OS confirmation and rechecks the paired account before and after it. Built-in protections are read-only. Patterns and unfinished drafts remain in the local child, including across status refreshes. Commands and their network stay per folder; a read-only folder explains that changes must be enabled first, and an organization policy hint explains when commands are still disabled there.

Allow changes and initial Run commands have one confirmation inside the app-owned pane: flip the switch, then Allow or Cancel. They no longer repeat that question in an OS dialog. Native code supplies the wording and a one-use token bound to the exact request, local folder identity/access, window and authenticated account/device context. While the question is open, native placement is frozen so the remote page cannot move its Allow button under the pointer. Hiding, changing page/account, expiration or cancellation invalidates the question; accepting revalidates context and consumes the token before the daemon request. The remote `computer_change` API still asks in its OS dialog. Browser/site/network, bot grants and exclusion changes retain their existing single confirmations.

The top frame calls `preferences.present({page, bot?, bounds:{x,y,width,height}, theme})` and `preferences.hide()`. Fixed pages are `folders`, `browser`, `general`, `notifications`, `account`, `activity`, plus `bot-sharing`. The bridge supplies the real viewport and a random per-window proof held only in its top-frame closure. The result contains no local state. Linux cannot distinguish frame callers at Tauri IPC level, so the proof is required in addition to origin and webview-label checks.

Native code fetches `settings_context` (account, device ID, command policy, whether the owner may manage policy, and optional bot identity) from the daemon, which makes a DPoP-authenticated GET to `/desktop/settings_context` (optionally `?bot=ID`). It validates device ID, exact account route and selected tab, or the exact bot route. Context expires after 30 seconds; an independent native watcher refreshes it every 25–30 seconds and closes the pane if permission is lost or verification fails. Every access-widening change is revalidated before its confirmation and again when accepted; bot grants also require the current bot route. The server never receives local file paths, activity, deny patterns, or grant details.

The child loads bundled `index.html`; only its webview label gets local IPC permissions, never its parent window. It cannot navigate away or open windows. The remote document cannot inspect the child’s DOM. On Linux, current Tauri packs children into GtkBox, so the app reparents the managed child into GtkOverlay through the public WebView handle; IPC remains managed by Tauri. Other platforms use native child bounds. Native code clips placement to the client bounds and serializes mounts; generations discard late responses after hide/navigation. Rails keeps the current pane visible during a bounded same-account computer-tab handoff, then presents the next page only after checking the incoming shell and device. Other navigation, modal/menu overlays and backgrounding hide it; overlay hiding preserves the app-owned draft and scroll position. Native full navigation closes it. Independent windows have independent proofs and panels.

Browser has one Use your browser switch: turning it off stops access without discarding registration or site choices; a stop made in the extension must be resumed there. Site access offers **Only these sites** and **All sites except…**, preserving both lists. Blocked sites take priority in both modes. Native confirmation still protects broader access and removal of a block. **Ask before browser actions** starts on. Turning it off requires a native confirmation and permits browser actions on permitted sites without repeated approval, including sending, buying and deleting; it changes neither command nor file approvals.

Before pairing, offline, and against older servers, the app shows its bundled navigation in this same OS window. The parent loads an unprivileged blank shell; only its local child receives local commands. Native pickers and confirmations remain separate system dialogs.

## Updating itself

`update.rs` checks for a newer release at start (after 20 seconds) and once a day, through fastframe-update over the app's own TLS roots and proxy, on every install. The former `app.json` opt-out is ignored. Updates appears before Background agent in General; checking is automatic, while installing still requires Restart to Update. A copy that may replace itself, the Mac app from the `.dmg` and the Windows installer's, downloads the release, which is refused unless `checksums.txt.sig` verifies with the key compiled in (`assets/update-public-key.hex`), and keeps it ready; the tray then shows **Restart to Update to X.Y.Z** above Quit and General shows the same button. Restarting hands the download to a helper (a copy of the app, `--apply-update`), which waits for the app to quit, installs it, and starts the new version with the windows it had (`--background` when none was open). The new version acknowledges the update, then restarts the background agent with `cww daemon install` when the agent's version differs (the Windows installer restarts it itself). If the new version doesn't acknowledge within a minute, the helper puts the old one back and starts it with a message, which the app shows once in a dialog and in General, and it waits a day before checking again. Copies a package manager owns, and the Mac's `.pkg`, say in General how to update instead. PACKAGING.md, "Updates", has the release names the updater depends on and how to try it without publishing.

## Testing and pictures

`cargo test -p cww-app` covers the parts that decide something: the navigation rules, the server and its pages, the user agent, the loopback callback, the download names, the allow-list, the activity log's sentences, the tray's labels, what pages may see and change of this computer (and what asks first), and the NVIDIA rule.

`node --test app/tests/*.test.mjs` drives the welcome, pairing and folder
controls, browser modes and approvals, exact typed domains, and the page bridge with synthetic state and recorded commands.
The real native windows are checked with the snapshots below.

`cargo run -p cww-app --features demo -- --demo` runs against a stand-in daemon with sample folders and activity (`--demo-fresh` for a first run; `CWW_DEMO_BROWSER=1` adds a synthetic connected browser without registering a host or opening a real browser). On Linux, `CWW_APP_SNAPSHOT=<dir>` makes a demo build save each settings page as a PNG and quit (`CWW_APP_SNAPSHOT_PAGES`, `CWW_APP_SNAPSHOT_THEME`, and optional `CWW_APP_SNAPSHOT_WIDTH`/`CWW_APP_SNAPSHOT_HEIGHT` for narrow windows; `main` is the Chat with Work window). WebKitGTK paints the pictures itself, so they work with the window on a hidden workspace. `main:/path` pictures the Chat with Work window on a server's page (`--server` a development server, `CWW_APP_SNAPSHOT_LOGIN=email:password` to sign in first, and `CWW_DEMO_DEVICE_ID` so the stand-in daemon is one of its computers), `probe:<file>` runs a script there and prints the title it leaves, and `shot:<name>` pictures that window as it is.
