A command can now reach the database and other services this computer runs for itself, without the internet. When the sandbox refuses a command a connection, Chat with Work says what it was, and one press opens this app to ask you. Setting up a coding bot reads what the repository needs without running any of it.

## New

- **Commands reach this computer's own services, and nothing else, by default.** A folder that allows commands now has a **Network** choice in Shared folders: None, Local services (the default), or Local services and the internet. With local services, `bin/rails test` reaches the PostgreSQL or Redis you run on this computer, in Docker or not, but not the local network or the internet. On Linux that's this computer's loopback (a command's own `localhost:5432` is the one you serve), its own addresses, and its containers' networks (`docker0`, Compose's bridges, Podman, libvirt and the like). On macOS it's the ports this computer serves on its loopback, as `localhost`, which is where Docker Desktop publishes containers. Ports that would let a command out of its sandbox are never reached: the Docker API over TCP, VNC and X11, browser DevTools and Node's inspector, and Desktop's own. Windows and Linux computers on Landlock can't give local services (below). [docs/commands.md](https://github.com/crmne/chatwithwork-desktop/blob/main/docs/commands.md#its-network) has the details. By @crmne ([#184](https://github.com/crmne/chatwithwork-desktop/pull/184)).
- **The internet is a switch of its own.** "Local services and the internet" is what "Commands use the network" was: everything. Exact addresses on the local network, such as a database on another machine, can be allowed one by one with `cww roots reach <folder> <ip:port>` or from the app's dialog, never a whole network. By @crmne ([#184](https://github.com/crmne/chatwithwork-desktop/pull/184)).
- **A refused connection says what it was, and one press asks you here.** On Linux with Bubblewrap, a connection the sandbox refuses fails at once instead of waiting minutes for a timeout, and the command's result names it: the address, the service by its port (PostgreSQL, Redis, ...), and whether it's on this computer, the local network or the internet; a refused name lookup is named by the name it asked for. Chat with Work turns that into a Decision with one button, which opens this app, and the app asks in a window of its own, **Allow a Connection**, naming the bot, the folder and the service as this computer places them, and **Allow** gives it to that bot's next command there, or for good, as you chose in Chat with Work. Turning local services on from Chat with Work asks the same way, in **Allow Local Services**. A page can only ask: every answer is yours, on this computer, and is in the audit log. This needs a Chat with Work that asks, which goes live alongside this release. By @crmne ([#184](https://github.com/crmne/chatwithwork-desktop/pull/184)).
- **Setting up a coding bot reads what the repository needs, without running it.** Desktop reads the repository's own files (Compose files, `config/database.yml`, `.env` files, Procfiles, `package.json` and the install manifests) with `git show`, and the Set up window says in one line what its code reaches: "It can reach PostgreSQL and Redis on this computer, and the internet to install gems (from docker-compose.yml and Gemfile)". The one **Allow** then gives local services and any local-network address the files name, and the internet, which the coding agents need: the internet includes the rest of the local network, so the folder's commands aren't held to the addresses the files name. A first run that needs more than its folder gives stops before installing anything and brings the card back. By @crmne ([#184](https://github.com/crmne/chatwithwork-desktop/pull/184)).
- **Open the guide to connecting a computer in this app.** Chat with Work's guide to connecting a computer now offers **Open Chat with Work Desktop** on its steps done on the computer, and opens here, where Add folder and Run commands work in place. By @crmne; thanks @crmne for reporting the guide had nothing to press ([#183](https://github.com/crmne/chatwithwork-desktop/pull/183)).
- **OpenCode, Gemini CLI and pi, as well as Claude Code and Codex.** A coding bot can use any of them with this computer's own sign-in, your own subscription or API key, with the same rules: only for the bot and folder you allowed, their tokens taken out of what a run prints. `cww coding setup --agent opencode|gemini|pi` does it from a terminal. By @crmne ([#182](https://github.com/crmne/chatwithwork-desktop/pull/182)).

## Changed

- **Folders that allowed commands without the network now reach local services.** Folders with the network keep everything. A folder that ran commands with no network gets this computer's own services after the update: a database on this computer that needs no password is then a command's to read and change. Choose **None** in Shared folders, or `cww roots local-services <folder> off`, where that matters. By @crmne ([#184](https://github.com/crmne/chatwithwork-desktop/pull/184)).
- **On Linux, a command's memory limit is what the whole command really uses.** It was an rlimit on each process, which counts the address space a program reserves rather than the memory it uses. Now the kernel counts the command's processes together, swap included, in a cgroup of its own, and ends them all when they reach the limit, and the result says `memory`. The limit is now half this computer's memory by default, at least 4 GB (`command_memory_mb`; on Windows too, for each process), since a big parallel build's compilers share it: a debug build of a large Rust crate with 8 jobs used 13.4 GiB at its peak. A config that still says the old 4096 moves to the new default; another number stays as you set it. The packaged service, and one installed with `cww daemon install`, now let Desktop make those cgroups (`Delegate=yes`). By @crmne ([#189](https://github.com/crmne/chatwithwork-desktop/pull/189)).

## Fixed

- **Builds no longer fail to allocate far below the memory limit.** rustc and LLVM, a JVM, Go and Node reserve much more address space than they use, so under the old 4 GB rlimit a coding bot's Rust build aborted with "memory allocation of ... bytes failed" with a fraction of that in use. On Linux a run now has no memory rlimit; its cgroup holds the limit instead, at half this computer's memory (above). By @crmne; thanks @crmne for reporting coding bots' builds aborting on Linux ([#189](https://github.com/crmne/chatwithwork-desktop/pull/189)).
- **Tools that keep sockets or locks in `XDG_RUNTIME_DIR` work in commands.** The sandbox leaves out your own `/run/user/<uid>`, so each command now gets a private one in its own home. By @crmne ([#189](https://github.com/crmne/chatwithwork-desktop/pull/189)).
- **Chat with Work hears at once when you share or stop sharing a folder.** Adding a folder that doesn't allow changes (on Windows), or removing or renaming any folder, left Chat with Work's list of this computer's folders as it was until the next reconnect. Now the agent reconnects, and the guide ticks the step as you go. By @crmne ([#183](https://github.com/crmne/chatwithwork-desktop/pull/183)).
- **Two quick changes to the shared folders can no longer undo each other.** A reload that read the settings before a removal could apply them after it, bringing the removed folder back. By @crmne ([#183](https://github.com/crmne/chatwithwork-desktop/pull/183)).
- **Security update of the `zip` library**, to 9.4.2, for an archive whose central directory names a different file than its local header ([GHSA-m665-v7pm-7grj](https://github.com/zip-rs/zip2/security/advisories/GHSA-m665-v7pm-7grj)). By Renovate ([#185](https://github.com/crmne/chatwithwork-desktop/pull/185)).

## Known limitations

- **Where Linux refuses network namespaces, commands run with no network.** Ubuntu 23.10 and later refuse them with AppArmor, though Bubblewrap itself still runs. There, local services give nothing and nothing refused is reported, and a folder with the internet fails at once and says why.
- **Windows and Landlock give no local services.** A Windows process container can't reach this computer's loopback without an administrator's exemption for every app, and Landlock can't tell one address from another. On Windows a folder has None or the internet; on Landlock it has no network at all, and a folder with the internet fails at once and says why.
- **On Landlock, a program a command builds can't run.** `cc hello.c -o hello && ./hello` stops at "Permission denied", as it did in 0.15.0.
- **Only Linux with Bubblewrap says which connection was refused.** On macOS a refused connection fails at once too, but which one isn't said; Windows and Landlock don't say either.
- **On macOS, local services are loopback ports, and only the internet reaches another machine.** Exact local-network addresses can't be given there, a command still can't serve itself, and a service started after a command is reached only by running the command again.
- **On Linux, the memory limit needs the systemd service.** Where the agent runs another way (`cww daemon run` from a terminal, the AppImage, a container), commands have no memory limit. A service installed with `cww daemon install` before 0.16.0 gets one after `cww daemon install` again.
- **Narrowing a folder's network stops the commands running there,** since their sandboxes were made with the wider one.
- **Codex and OpenCode aren't available on macOS yet.** In the Mac's sandbox Codex stops at "Failed to synchronize managed preferences", and OpenCode's private server can't listen on a local port. Desktop doesn't loosen the sandbox for them, so the Set up window says they can't run there.
- **A Codex that keeps its sign-in in the system keyring reads as not signed in.** Use Codex's file store (`cli_auth_credentials_store`).
- **`.xls`, `.xlsb` and `.ods` files are still read whole,** so a crafted one can still use a lot of memory, as it could before.
- **Folder environments are set from a terminal.** The app doesn't have a field for them yet.
- **The AppImage can't run the background agent as a service, and the Flatpak bundle can't start it at login or run commands.** For those, use a package or the terminal archive. In the Flatpak, run the agent yourself with `flatpak run --command=cww com.chatwithwork.desktop daemon run` ([#138](https://github.com/crmne/chatwithwork-desktop/issues/138)).
- **The Flatpak bundle doesn't update itself.** No Flatpak repository publishes it yet, so Desktop shows the command that installs the new bundle.
- **Printing hasn't been tried on a physical printer.**
- **Linux animations can still remain at 60 fps.**
- **The browser extension is still installed manually.**
- **On Mac, use the signed and notarized DMG; the PKG remains unsigned.** Windows SmartScreen may warn while the installer builds reputation.
