Run commands no longer waits: turn it on in any shared folder, while it's indexing or before it allows changes, with one question for both. The Windows one-line installer says when the background agent didn't start, and the `zip` library has a security update.

## Fixed

- **A coding bot no longer asks you to trust the worktree it made.** Claude Code ran a bot's fix without the repository's own `.claude` settings and said "this workspace has not been trusted" on every run, and the Issue fixer asked its team to trust it. Now Desktop marks each checkout it cloned for a bot as trusted in Claude Code's and Codex's own settings before the bot's run, which covers every worktree the bot makes from it. A checkout that was in the folder before keeps asking, as before, and what a run may read, write and reach is unchanged. By @crmne; thanks @crmne for reporting it ([#200](https://github.com/crmne/chatwithwork-desktop/pull/200)).
- **Run commands can be turned on while a folder indexes, and in a read-only folder.** A newly shared folder is read-only, so its Run commands switch stayed greyed out until Allow changes was on. The only state beside it was "Indexing…", so it read as waiting for the index, and it stayed off after indexing too. Now the switch works in every folder, in Shared folders and in Chat with Work's guide to connecting a computer. In a read-only folder it says that turning it on allows changes too, and one question asks for both: "Let Chat with Work change files and run commands in “Projects”?". Commands still need your organization to allow them, and each one is still approved in Chat with Work. By @crmne; thanks @crmne for reporting it ([#197](https://github.com/crmne/chatwithwork-desktop/pull/197)).
- **A switch pressed while a folder indexes no longer misses.** Each progress report, every 500 files, drew Shared folders again and could replace a switch under the pointer. Now only the folder's label changes. By @crmne ([#197](https://github.com/crmne/chatwithwork-desktop/pull/197)).
- **The Windows one-line installer says when the background agent didn't start,** with the reason and how to start it, instead of reporting success. By @crmne ([#193](https://github.com/crmne/chatwithwork-desktop/pull/193)).
- **`cww roots remove` is in the activity log,** as removing a folder in the app is. By @crmne ([#193](https://github.com/crmne/chatwithwork-desktop/pull/193)).
- **`cww` on Windows says "The internet"** where it said "Local services and the internet", as the app does, since Windows gives commands none of this computer's own services. By @crmne ([#193](https://github.com/crmne/chatwithwork-desktop/pull/193)).
- **The Mac app's icon is a tile of macOS's own shape.** macOS 27 shrank the old icon into a grey box. Now the sticker sits on a graphite-to-black tile that macOS draws itself. By @crmne; thanks @crmne for reporting it ([#201](https://github.com/crmne/chatwithwork-desktop/pull/201)).
- **Security update of the `zip` library**, to 9.5.0 ([GHSA-m665-v7pm-7grj](https://github.com/zip-rs/zip2/security/advisories/GHSA-m665-v7pm-7grj)). By Renovate ([#195](https://github.com/crmne/chatwithwork-desktop/pull/195)).

## Known limitations

- **Where Linux refuses network namespaces, commands run with no network.** Ubuntu 23.10 and later refuse them with AppArmor, though Bubblewrap itself still runs. There, local services give nothing and nothing refused is reported, and a folder with the internet fails at once and says why.
- **Windows and Landlock give no local services.** A Windows process container can't reach this computer's loopback without an administrator's exemption for every app, and Landlock can't tell one address from another. On Windows a folder has None or the internet; on Landlock it has no network at all, and a folder with the internet fails at once and says why.
- **On Landlock, a program a command builds can't run.** `cc hello.c -o hello && ./hello` stops at "Permission denied", as it did in 0.15.0.
- **Only Linux with Bubblewrap says which connection was refused.** On macOS a refused connection fails at once too, but which one isn't said; Windows and Landlock don't say either.
- **On macOS, local services are loopback ports, and only the internet reaches another machine.** Exact local-network addresses can't be given there, a command still can't serve itself, and a service started after a command is reached only by running the command again.
- **On Linux, the memory limit needs the systemd service.** Where the agent runs another way (`cww daemon run` from a terminal, the AppImage, a container), commands have no memory limit. A service installed with `cww daemon install` before 0.16.0 gets one after `cww daemon install` again.
- **Narrowing a folder's network stops the commands running there,** since their sandboxes were made with the wider one.
- **Codex and OpenCode aren't available on macOS yet.** In the Mac's sandbox Codex stops at "Failed to synchronize managed preferences", and OpenCode's private server can't listen on a local port. Desktop doesn't loosen the sandbox for them, so the Set up window says they can't run there.
- **A Codex that keeps its sign-in in the system keyring reads as not signed in.** Use Codex's file store (`cli_auth_credentials_store`).
- **`.xls`, `.xlsb` and `.ods` files are still read whole,** so a crafted one can still use a lot of memory, as it could before.
- **Folder environments are set from a terminal.** The app doesn't have a field for them yet.
- **The AppImage can't run the background agent as a service, and the Flatpak bundle can't start it at login or run commands.** For those, use a package or the terminal archive. In the Flatpak, run the agent yourself with `flatpak run --command=cww com.chatwithwork.desktop daemon run` ([#138](https://github.com/crmne/chatwithwork-desktop/issues/138)).
- **The Flatpak bundle doesn't update itself.** No Flatpak repository publishes it yet, so Desktop shows the command that installs the new bundle.
- **Printing hasn't been tried on a physical printer.**
- **Linux animations can still remain at 60 fps.**
- **The browser extension is still installed manually.**
- **On Mac, use the signed and notarized DMG; the PKG remains unsigned.** Windows SmartScreen may warn while the installer builds reputation.

- **Allowing changes in a folder restarts the background agent,** which checks every shared folder again and shows "Indexing…" from zero meanwhile, though searches keep using the index it already has.
